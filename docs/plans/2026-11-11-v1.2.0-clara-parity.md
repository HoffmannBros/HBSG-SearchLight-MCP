## Why this work exists

A review on 2026-11-11 did three things:

1. Read the API docs and ran `npm run probe` against the live API. The only
   change since v1.1.1 is **subsets** (release note 2026-10-12), which the
   extension does not support.
2. Read SearchLight's own cloud connector ("ClaraT", https://searchlight.digital/clarat)
   and its knowledge base. Clara is a thin passthrough to the same API plus a
   large set of written rules about how the API misleads. Several of those
   rules describe things this extension currently gets wrong or does not warn
   about.
3. Looked at how the extension has been used. All four past exports and the
   `google-member-cost` skill pull the same shape: account, channel, campaign
   with spend, leads, booked and paying customers, sold and closed revenue.
   That shape is exactly where two of Clara's rules bite (spend dropped from
   campaign splits; unreliable `or` filters).

The goal: match Clara on everything an `sl_` API key can reach, build Clara's
accuracy rules into the tools so the model does not have to remember them, and
add report tools for the pulls that keep being rebuilt by hand.

### From SearchLight's knowledge base (their measurements, not re-verified here)

Treat each as a claim to confirm live where your work item says so.

| # | Claim | Their evidence |
|---|---|---|
| K1 | A `channel`/`campaign` split only returns a row when the combination has at least one tracked event, so **spend on campaigns with zero conversions is dropped** from the split. Counts and revenue still match the unsplit total exactly. | 2026-10-20, one organization: split spend under-counted the unsplit total on 39 of 44 accounts. |
| K2 | `["or", ...]` and `["regex", ...]` filters sometimes answer **200 with an empty body** where a single equality answers rows. Seen on `attributionChannel`, `campaign` and `businessUnit`. One call per value is the reliable form. | 2026-10-26 and 2026-11-06. The same form worked on `conversionChannel` on 2026-10-22, so it is unreliable, not broken. |
| K3 | A plain list as a filter value (`["Google Ads","Bing"]`) and an object such as `{"in":[...]}`, `{"$in":[...]}`, `{"$gt":0}`, `{"$regex":...}` answer 200 `[]` with no error. An array is always read as `[operator, ...args]`. | 2026-10-15, 2026-10-22, 2026-11-04. |
| K4 | **Grading metrics beside count metrics inflate the counts.** Any of `gradedConversions`, `bookableConversions`, `unbookableConversions`, `bookedConversions`, `bookableUnbookedConversions`, `percentConversionsGraded`, `conversionQuality` requested with `customers`, `leads`, `opportunityCount`, `unmatchedCustomers`, `bookRate`, `matchRate`, `payingCustomerRate`, `stepBookRate` or `avgCostPerLead`. | `leads` +18.7% and +22.5% (2026-07-27); one account-month 2,869 alone vs 3,723 with `gradedConversions`. |

An opportunity can still answer several rows (one per job), so dedupe on `opportunityId`. | 2026-08-03, 2026-10-13. |
| K7 | Dimension splits carry **placeholder rows**: an all-zero row with the dimension absent, and blank or `N/A` rows with the metric at 0. Totals are unaffected. | 2026-10-01. |
| K8 | **Empty buckets are omitted**, not returned as zero. | 2026-09-30. |
| K9 | A long-range `total` can come back 200 with an **all-zero row** while monthly buckets over the same span carry data. | 2026-10-14 (admin key, range over 90 days). |

### Found by reading this repo

- `src/fields.ts` `METRIC_GUIDE.closedRevenue` and the `INSTRUCTIONS` string in
  `src/index.ts` say `closedRevenue` is safe to sum across interval rows. K5
  and our own 2026-10-09 measurement (+3%) say it is not exact.
- `hintFor` in `src/client.ts` gives the "organization is not accessible" hint
  for every 404, including `inaccessible-accounts`.
- `SearchLightApiError.isSizeLimit` matches size rejections by message text
  only. It does not know the codes in K10.
- The `/api` cache TTL is 10 minutes (`accessTtlMs` in `src/client.ts`).
- `src/filters.ts` passes any array or object through as JSON without checking
  that an array starts with an operator.
- `compare_periods` reports `m_pct` for rate metrics with no label saying it is
  relative, and gives no warning when stage revenue is compared across periods.
- `scripts/probe.ts` does not record subsets, `-`, or the undocumented fields.
- The `google-member-cost` skill (outside this repo) filters
  `attributionChannel` with `["or","Google Ads","Google Lsa"]` and sums spend
  from a campaign split. Both are affected by K1 and K2.

## Parent session: how to run this

### Your job

You coordinate. You do not implement Wave 1, 2 or 3 items yourself. You:

1. Prepare an integration branch.
2. Start one sub-session per work item.
3. Check each sub-session's result yourself before merging it.
4. Merge in a fixed order and run the full test suite after every merge.
5. Do Wave 4 (docs, instructions, version, release checks) yourself.
6. Stop and ask the user before anything is pushed, tagged or released.

Read `AGENTS.md` and `next_steps.md` first. Then, from the repo root on a clean
`main`:

```bash
git status --short
```

```bash

```



  sub-sessions must never write in the same checkout.
- **Its own branch**, named as listed in the work item.
- **`npm ci` run inside the worktree** before anything else.
- **A copy of the repo-root `.env`** in the worktree, for live checks. `.env`
  is gitignored; copy the file, never print it or paste its contents into a
  brief.

Use this brief, filling in the three placeholders:

```text
worktree at <WORKTREE PATH>, on branch <BRANCH NAME>.
```

### Step 2: review each result before merging

A sub-session's report is a claim. Before merging a branch:

1. Read the diff: `git diff feat/v1.2.0...<branch>`.
2. Confirm it only touches the files its work item allows.
3. Confirm none of the parent-only files changed (see the rules section).
4. Run `npm test` inside that worktree.
5. Check each acceptance criterion in the work item against the diff.
6. For each live check in the report, confirm a result is stated, not assumed.

If something is wrong, send the sub-session a specific correction. Do not fix
it yourself and do not merge a branch that fails a criterion.

### Step 3: merge order

Merge into `feat/v1.2.0` one at a time with `git merge --no-ff <branch>`, and
run `npm test` after each merge.

Wave 1:

1. W1-C `feat/field-reference`
2. W1-B `feat/request-guards`

After Wave 1 is merged, run `npm run probe` once from the integration branch

### Step 4: Wave 2, then Wave 3

- **Wave 2** starts only after all of Wave 1 is merged. Run W2-A, review and

## Rules for every sub-session

1. **Scope.** Do your work item and nothing else. If you find another bug,
   put it in your report. Do not fix it.
2. **Follow AGENTS.md.** In particular:
   - typed tools get their organization and accounts from `resolveScope`
     (`src/context.ts`), never `resolveOrganization` alone;
   - never introduce `definitions` or `dependencies` into a tool schema, and
     do not touch `src/schema-compat.ts`;
   - splitting an events request by account is only valid when `account` or
     `accountKey` is in `fields` (`canSplitByAccount`);
   - anything the API is certain to reject is refused locally before sending.
3. **Files reserved for the parent.** Do not edit these: `README.md`,
   `AGENTS.md`, `CLAUDE.md`, `next_steps.md`, `package.json`,
   `package-lock.json`, `manifest.json`, `src/version.ts`, `.mcpbignore`,
   `scripts/pack.sh`, `scripts/smoke.ts`, and the `INSTRUCTIONS` string in
   `src/index.ts`. If your change needs one of them updated, give the exact
   text in your report. (W3-A and W3-B may each add one `register…Tools` line
   and its import to `src/index.ts`; nothing else in that file.)
4. **Tests go in the new file named in your work item.** Do not add tests to
   an existing test file unless a change you made breaks an existing
   assertion; then fix that assertion and list it in your report. Copy the
   fake-fetch pattern from `tests/client.test.ts` and `tests/tools.test.ts`.
   Every request your code can send needs a test asserting the exact path and
   query parameters.
5. **Verify against the live API before you write the code.** The docs and the
   knowledge-base claims have both been wrong before.
   - Docs: https://docs.searchlightdigital.io/api/overview/ (beta).
   - Live checks: a short `tsx` script in the worktree that builds a
     `SearchLightClient` the way `scripts/probe.ts` does, reading the key from
     `.env`. Delete the script before you commit.
   - **Live calls are GET only.** The API has no writes, and nothing outside
     `/api` is reachable with this key.
   - Keep live checks small: one account, a range of a week or less unless the
     check is about long ranges. Stay under about 40 live requests in total.
     The limit is 2,000 an hour for the whole user, shared by every
     sub-session.
   - A 200 does not prove a filter or a parameter did anything. Prove it by
     comparing against a call without it.
   - The installed Claude Desktop extension is older than this repo. Do not
     use it for checks.
6. **Privacy.** Live rows carry customer names, phones, emails, addresses and
   call transcripts. Never copy them into code, tests, commit messages, the
   plan, or your report. Report shapes, counts and field names only. Tests use
   made-up data. Never print or commit the API key.
7. **A rule built into a tool must be visible.** When a tool sends extra
   requests, splits a request, drops rows or refuses, it says so in the
   result's `notes` and the extra requests show in `apiCalls`.
8. **Run `npm test`** before you finish. All tests must pass, old and new.
9. **Commit on your branch** with a message in the style of `git log` (a short
   imperative sentence). Do not push. Do not merge.
10. **If the plan and the API disagree**, the API wins. Implement what the API
    does and state the difference in your report. If a knowledge-base claim
    does not reproduce on this account, say so and build the guard anyway only
    if it is harmless when the claim is false; otherwise stop and report.

## Wave 1 work items (parallel)

### W1-A: Subsets, the `-` organization, and scope fixes

- **Branch:** `feat/subsets-and-scope`
- **Test file:** `tests/subsets.test.ts`
- **Files:** `src/scope.ts`, `src/context.ts`, `src/client.ts` (types,
  `hintFor`, `accessTtlMs` only), `src/chunking.ts`, `src/tools/common.ts`,
  `src/tools/access.ts`, `src/tools/events.ts`, `src/tools/benchmarks.ts`,
  `src/tools/insights.ts`, `src/tools/compare.ts`, `src/tools/raw.ts`,
  `src/filters.ts` (`RESERVED_PARAMS` only)

**Change**

1. **Types.** `OrganizationInfo` gains
   `subsets?: Array<{ subset: string; name?: string; accounts?: string[] }>`.
2. **`subset` argument.** Add `subsetArg` to `src/tools/common.ts` and to every
   typed tool that takes `organization`: both events tools, both benchmark
   tools, both insight tools and both compare tools. Send it as `subset=<id>`.
   Add `subset` to `RESERVED_PARAMS`.
3. **Scope check.** Extend `checkScope` / `resolveScope` to take the subset:
   - a subset the organization does not list is refused locally, naming the
     subsets it does list;
   - when a subset and accounts are both given, each account must be in the
     subset's `accounts` (the API returns 404 otherwise); refuse locally;
   - when the organization argument is not an organization or an account but
     is a subset id under exactly one organization, reroute to that
     organization with `subset=<id>` and add a note, the same way an account
     key is rerouted today. The 2026-10-12 release note says organizations
     that used to sit inside another are now subsets and their old key 404s.
   - `Scope` gains `subset: string | undefined`.
4. **Chunking.** `EventsQuery` and `InsightsQuery` carry `subset`, and it is
   sent on every chunk. When a request is split by account and a subset is
   set, the account list comes from the subset, not the whole organization.
5. **`-` as the organization.** `organization: "-"` means every account the
   key reaches. `checkScope` accepts it without an organization lookup,
   checks any `accounts` against the union of all reachable accounts, and
   refuses `subset` with it (the knowledge base says subset does not apply).
   For account splitting, `client.listAccounts("-")` returns that union.
   Update `organizationArg`'s description to mention it in one sentence.
6. **`searchlight_list_access`.** Show each organization's subsets (id, name,
   account count) in the text and keep them in `structuredContent`. Mention
   `-` in the tool description. Change "10-minute cache" to match item 8.
7. **404 hints.** `hintFor` keys on the error code: `inaccessible-accounts`
   says the account is not under that organization (or not in the subset);
   `inaccessible-organization` keeps today's text; any subset-specific code
   you observe live gets its own hint.
8. **Cache.** Raise the default `accessTtlMs` to 60 minutes.
   `searchlight_list_access(refresh=true)` still bypasses it.
9. **Raw tool.** `rawPathProblem` accepts `-` as the path segment and applies
   the same subset checks when `subset` is in the params.

**Live checks**

- `GET /api/hoffmann-brothers/events?...&subset=<made-up id>`: record the
  status and `code`. This is the only subset check possible here, because
  `hoffmann-brothers` has none defined.
- `GET /api/-/events` with metrics only (one row for the whole reach), with
  `accountKey` (one row per account), with `accounts=<two keys>`, and with an
  account key that is not reachable (expect 404 `inaccessible-accounts`).
- `GET /api/-/benchmarks` and `/api/-/insights` for one small request each:
  record whether `-` is accepted there.

**Acceptance (each needs a test)**

- `subset` is sent on events, benchmarks, insights and both compare tools.
- An unknown subset, and an account outside the subset, are refused with no
  request sent.
- A subset id passed as `organization` is rerouted with a note.
- `-` is accepted; accounts are checked against the union; `subset` with `-`
  is refused locally.
- Account splitting under a subset uses the subset's accounts.
- `list_access` output includes subsets when the fake `/api` has them and is
  unchanged when it has none.
- Each 404 code gets its own hint.
- All existing scope tests pass unedited.

**Out of scope:** any accuracy guard or note (Wave 2).

### W1-B: Request guards (refuse or split before the API does)

- **Branch:** `feat/request-guards`
- **Test file:** `tests/request-guards.test.ts`
- **Files:** `src/filters.ts`, `src/dates.ts`, `src/client.ts`
  (`isSizeLimit` and `preflight` only), `src/chunking.ts` (pre-split only)

**Change**

1. **Filter shape (K3).** In `filtersToParams`, validate each per-field value:
   - an array whose first element is not one of the operators `or`, `and`,
     `not`, `empty`, `notEmpty`, `regex`, `gt`, `gte`, `lt`, `lte` is refused
     with a `FilterError` that shows the corrected form
     (`["or", "A", "B"]`);
   - a non-array object as a per-field value (`{"in": [...]}`, `{"$gt": 0}`)
     is refused the same way.
   Validate nested expressions recursively. Confirm the operator list against
   the docs' filtering page first. The cross-field `filter` argument keeps its
   current check; its branches are objects by design.
   Apply the same validation where `searchlight_api_call` builds events
   params only if it can be done inside `client.preflight` without touching
   `src/tools/raw.ts`; otherwise report it as a follow-up.
2. **Size codes (K10).** `isSizeLimit` also returns true for the codes
   `too-many-combinations`, `response-too-large` and `too-many-documents`, so
   the existing adaptive splitter handles them.
3. **Pre-split on combinations (K10).** Before the first events request, when
   the account list is known (explicit `accounts`, or the cached `/api` list
   for the organization) compute accounts x interval buckets
   (`intervalBoundaries`). If it exceeds 1,000 and the request can be split
   without changing its meaning (by date window always; by account only when
   `canSplitByAccount`), start from the split tasks instead of sending a
   request that will be refused. If it cannot be split, refuse locally with a
   message that names the count and the three ways out (fewer accounts, a
   coarser interval, a shorter range).
4. **Filter on a redacted field (K14).** Do not block it. Nothing to build;
   W2-A adds the note.

**Live checks**

- One request that should trip `too-many-combinations` (for example four
  accounts by day over 300 days is 1,200): record the status, `code` and
  message, and whether it counts as a size limit. Send it through a client
  with preflight disabled, the way `scripts/probe.ts` does.
- A plain-list filter and an `{"in": [...]}` filter on `attributionChannel`
  for one account-week, compared with the unfiltered call: confirm they
  answer 200 `[]` or record what they do answer.

**Acceptance (each needs a test)**

- Plain list and object filter values are refused with no request sent, and
  the message shows the operator form.
- Every documented operator form, including nested ones, still passes and
  encodes exactly as before.
- The three size codes are size limits; `range-too-long` still is not.
- A request over 1,000 combinations is pre-split when it can be, and refused
  locally when it cannot, with zero requests sent in the refusal case.
- A request at or under 1,000 combinations is sent as one request.
